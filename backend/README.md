# AI Agent Platform — Backend

FastAPI + PostgreSQL + Redis backend for the AI Agent Platform. All endpoints
are versioned under `/api/v1`; interactive docs are served at `/docs`.

## Architecture

```
Frontend (agent-ui) → FastAPI (/api/v1) → Service layer → PostgreSQL + Redis
                                                   ↘ LLM provider (Ollama)
```

The API layer only validates input, enforces auth and calls services — all
business logic lives in `app/services/`. Chat requests are served by an LLM
provider selected through `app/llm/factory.py`; the default is Ollama, running
locally for development. Providers implement the small interface in
`app/llm/base.py`, so adding another one (OpenAI, Anthropic, …) does not touch
the API or service layers.

```
backend/
├── app/
│   ├── main.py              # FastAPI entrypoint: CORS, middleware, lifespan
│   ├── api/                 # Routers (thin HTTP layer)
│   ├── services/            # Business logic (auth, user, chat, usage, ...)
│   ├── models/              # SQLAlchemy models
│   ├── schemas/             # Pydantic request/response schemas
│   ├── core/                # config, security, redis, middleware, rate limit
│   ├── database/            # async engine + session factory
│   └── llm/                 # provider interface, factory, Ollama + mock
├── migrations/              # Alembic migrations
├── tests/                   # pytest suite
├── docs/API.md              # API contract
├── requirements.txt
├── alembic.ini
├── Dockerfile
└── docker-compose.yml
```

## Running locally

### Option 1 — Docker (recommended)

```bash
docker compose up --build
```

Brings up PostgreSQL, Redis and the backend. Migrations run automatically on
startup, the default administrator is seeded, and the API is served at
http://localhost:8000 (docs at `/docs`).

### Option 2 — Native

Prerequisites: Python 3.12+, a PostgreSQL 13+ database and Redis.

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # Linux/macOS

pip install -r requirements.txt

cp .env.example .env            # then edit secrets/URLs as needed

alembic upgrade head            # create/migrate the schema
uvicorn app.main:app --reload   # start on http://localhost:8000
```

The first startup seeds an administrator from `DEFAULT_ADMIN_EMAIL` /
`DEFAULT_ADMIN_PASSWORD` in `.env`.

### Running the tests

```bash
pytest                          # 54 tests
```

Tests run inside a rolled-back transaction, so they never pollute the
database. Rate limiting is disabled in tests; PostgreSQL and Redis must be
reachable (the `DATABASE_URL` / `REDIS_URL` in `.env` are used). The LLM
provider is also mocked in tests, so the suite never needs a running Ollama.

## Local Ollama development

Chat answers are generated by [Ollama](https://ollama.com) running on your own
machine. Nothing else in the stack talks to Ollama directly: the browser calls
the FastAPI chat API, which routes to the provider, which calls Ollama's HTTP
API.

### 1. Install and start Ollama

Install from <https://ollama.com/download>, then start the service:

```bash
ollama serve          # serves the HTTP API on http://localhost:11434
```

### 2. Pull a model

```bash
ollama pull phi3:mini    # the default model
ollama pull qwen2.5:0.5b # extra models listed in OLLAMA_MODELS
ollama pull tinyllama
```

On a machine without a dedicated GPU the model size dominates response time, so
pick the smallest model that still answers well — `qwen2.5:0.5b` and
`tinyllama` reply in a few seconds on CPU, `phi3:mini` is more capable but
slower. Use a larger model only where a GPU is available.

### 3. Verify Ollama is running

```bash
curl http://localhost:11434/api/tags    # lists the models you pulled
```

Or, once the backend is up, use the backend's own probe (it does not expose
the raw Ollama API to the browser):

```bash
  curl http://localhost:8000/health/llm
# {"status":"healthy","provider":"ollama","base_url":"...","model":"phi3:mini","model_available":true}
```

### 4. Configure the backend

Set these in `backend/.env` (see `.env.example`):

| Variable | Example | Purpose |
|---|---|---|
| `OLLAMA_BASE_URL` | `http://localhost:11434` | Ollama HTTP API base URL |
| `OLLAMA_DEFAULT_MODEL` | `phi3:mini` | Model used when a request names none |
| `OLLAMA_MODELS` | `qwen2.5:0.5b,tinyllama` | Extra models (comma separated) shown in the dropdown |
| `OLLAMA_REQUEST_TIMEOUT` | `180` | Per-request timeout (seconds) |
| `OLLAMA_KEEP_ALIVE` | `30m` | How long Ollama keeps the model loaded |

Every model named in `OLLAMA_DEFAULT_MODEL` or `OLLAMA_MODELS` is registered in
the model catalog on first startup, so it appears in the chat UI's dropdown and
can be selected per conversation. Each must be pulled locally first, e.g.
`ollama pull qwen2.5:0.5b`. Requests may only use catalogued models, so listing
a model here is what makes it runnable.

**Response speed on CPU-only machines.** Generation rate is roughly
proportional to model size, and loading a cold model from disk costs tens of
seconds on top of that. Three things keep the demo responsive:

1. Use the smallest model that still answers well (qwen2.5:0.5b on CPU).
2. `OLLAMA_KEEP_ALIVE=30m` keeps the model in memory between requests, so only
   the first request pays the load cost (Ollama otherwise unloads it after ~5
   min idle). Set it to `0` to unload after every request.
3. The catalog's `max_tokens` (1024 for the seeded model) caps the generated
   length, bounding worst-case response time.

**Mind the memory budget.** A loaded model claims RAM roughly equal to its
file size, and `OLLAMA_KEEP_ALIVE` holds it there between requests. On a small
host (e.g. 8 GB) a multi-GB model like `phi3:mini` can starve PostgreSQL and
crash it mid-request. Check the footprint before adding a model:

```bash
curl http://localhost:11434/api/ps   # models currently held in memory
```

**Timeouts.** Three layers can cut a slow-but-valid response short, and they
must agree: the frontend chat timeout (`agent-ui/src/api/chat.ts`), Nginx's
`proxy_read_timeout`, and `OLLAMA_REQUEST_TIMEOUT`. They are aligned at 180 s;
change all three together.

**Host vs Docker — pick the right `OLLAMA_BASE_URL`:**

| Where the backend runs | `OLLAMA_BASE_URL` |
|---|---|
| Directly on the host (native Python/uvicorn) | `http://localhost:11434` |
| Inside a Docker container (`docker compose`) | `http://host.docker.internal:11434` |

A container's `localhost` is **not** the host's `localhost`. When the backend
runs in Docker and Ollama runs on the host, `host.docker.internal` is the name
that resolves back to the host (Docker Desktop provides it automatically; the
`extra_hosts` entry in `docker-compose.yml` adds it on Linux hosts too).

The model named in `OLLAMA_DEFAULT_MODEL` (plus any in `OLLAMA_MODELS`) is
registered in the model catalog on startup, so it appears in the chat UI's
model dropdown. Each must be a model you have actually pulled — requests may
only use catalogued models, so the frontend cannot run arbitrary models
installed in Ollama.

### 5. Run the stack

```bash
# from the repository root
docker compose up --build
```

### 6. Chat

1. Log in (the seeded administrator is `admin@example.com` / `change-me-now`).
2. Open the Chat Portal.
3. Click *New chat*, type a message and send it.
4. Ask a follow-up question: conversation history is loaded from PostgreSQL and
   sent with every request, so the model keeps context.
5. Refresh the browser: messages are persisted server-side, not in React state.

### Moving Ollama to a private server

Only `OLLAMA_BASE_URL` needs to change (for example to
`http://ollama.internal:11434`). No code changes are required — the URL is read
from configuration, never hard-coded. To use a different provider later,
implement `app/llm/base.py` and register it in `app/llm/factory.py`; the chat
API and service layers stay untouched.

## Configuration

All configuration comes from `.env` (see `.env.example`). Notable variables:

| Variable | Default | Purpose |
|---|---|---|
| `DATABASE_URL` | `postgresql+asyncpg://...` | Async PostgreSQL DSN |
| `REDIS_URL` | `redis://localhost:6379/0` | Redis DSN |
| `JWT_SECRET_KEY` | `change-me-in-production` | JWT signing key |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `30` | Access token lifetime |
| `REFRESH_TOKEN_EXPIRE_DAYS` | `7` | Refresh token lifetime |
| `RATE_LIMIT_PER_MINUTE` / `_HOUR` | `60` / `1000` | Redis-backed limits |
| `CORS_ORIGINS` | `http://localhost:3000,5173` | Allowed origins |
| `DEFAULT_ADMIN_*` | — | First-boot administrator |
| `OLLAMA_BASE_URL` | `http://localhost:11434` | Ollama HTTP API base URL |
| `OLLAMA_DEFAULT_MODEL` | `phi3:mini` | Model used when none is requested |
| `OLLAMA_MODELS` | `qwen2.5:0.5b` | Extra models shown in the dropdown |
| `OLLAMA_REQUEST_TIMEOUT` | `180` | LLM request timeout (seconds) |
| `OLLAMA_KEEP_ALIVE` | `30m` | Keep the model loaded between requests |

## Migrations

```bash
alembic revision --autogenerate -m "description"   # create
alembic upgrade head                               # apply
alembic downgrade -1                               # roll back one
```

Never use `Base.metadata.create_all()` in production — migrations are the
source of truth for the schema.
